# TXT → EPUB (Android)

텍스트 파일을 챕터가 나뉜 EPUB 3 전자책으로 변환하는 안드로이드 앱입니다.
웹 버전에서 막혔던 두 가지 — 파일 선택창 제약과 나무위키 조회 차단 — 이 네이티브에서 해결됩니다.

패키지 `com.kaicia.txt2epub` · minSdk 26 (Android 8.0) · targetSdk 34 · Kotlin 1.9.24 + Compose

## 빌드

```bash
cd txt2epub-android
./gradlew assembleDebug        # 결과: app/build/outputs/apk/debug/app-debug.apk
./gradlew testDebugUnitTest    # 단위 테스트 97개
```

Android Studio(Koala 이상)에서 `txt2epub-android` 폴더를 열어도 됩니다.
Gradle Wrapper(8.7)가 들어 있어 따로 만들 필요는 없습니다.

안드로이드 SDK가 없는 환경이라면 GitHub Actions로 빌드하세요.
저장소 **Actions 탭 > "txt2epub Android build" > Run workflow**를 누르면
러너에서 테스트와 APK 빌드를 하고, 실행 결과 페이지 아래 Artifacts에
`app-debug-apk`가 올라옵니다. 내려받아 기기에 설치하면 됩니다.

## 쓰는 순서

1. **파일** — TXT 파일 선택. 파일 관리자에서 txt를 '열기/공유'로 보내도 바로 열립니다.
   인코딩은 자동 판정하고, 틀렸으면 직접 바꿀 수 있습니다.
2. **챕터 구분** — 앱이 알아서 나눕니다. 다른 후보로 바꾸거나 정규식을 직접 줄 수도 있습니다.
   '전체 목차 · 본문 미리보기'로 잘린 결과를 눈으로 확인하세요.
3. **책 정보** — 제목·지은이·출판사. '파일에서 찾기'(오프라인)와 '웹에서 찾기'(네이버책·나무위키·위키백과).
   표지는 '웹에서 표지 찾기'로 후보를 썸네일로 받아 고르거나, 기기에서 직접 고릅니다.
4. **파일 이름 규칙** — 템플릿으로 통일합니다. 규칙은 저장돼서 다음에 열어도 그대로입니다.
5. **나눠 저장** — 챕터 N개씩 여러 권으로 쪼갭니다. 폴더를 고르면 권별로 파일이 생깁니다.
6. **생성** — EPUB 저장.

## 구조

```
core/TextReader.kt      인코딩 감지 및 본문 로드
core/ChapterDetector.kt 챕터 구분 자동 판정
core/EpubWriter.kt      EPUB 3 패키지 생성
core/FileNamer.kt       출력 파일명 템플릿
core/MetaScanner.kt     본문에 적힌 서지 정보 읽기 (오프라인)
net/Http.kt             공용 HTTP 클라이언트
net/MetadataLookup.kt   나무위키 / 위키백과 조회
net/CoverSearch.kt      표지 찾기 (구글북스 / 오픈라이브러리 / 네이버책)
net/NaverBooks.kt       네이버 책 검색 API (키를 넣었을 때만)
data/Prefs.kt           설정 저장
ui/Theme.kt             Material You + 다크모드
MainViewModel.kt        상태 관리
MainActivity.kt         Compose UI
```

## 핵심 동작

### 파일 고르기
파일 선택창에 형식 제한을 걸지 않습니다. `text/plain` 같은 걸 걸었더니 기기와
파일 관리자에 따라 **txt가 목록에서 통째로 사라지고 예전에 만든 epub만 보이는**
일이 있었습니다. 그걸 텍스트로 알고 넣으면 압축 바이트가 글자로 풀려 챕터 판정이
엉망이 됩니다.

그래서 전부 보여주고, **고른 뒤에 텍스트인지 확인해서 막습니다.** zip(epub·docx),
PDF, 그림 파일의 머리 바이트를 보고, 앞 4KB에 0 바이트가 섞여 있으면 텍스트가
아닌 것으로 봅니다. UTF-16은 0 바이트가 정상이라 BOM을 먼저 봅니다.

### 파일 입출력
SAF(Storage Access Framework)를 씁니다. `OpenDocument`로 읽고 `CreateDocument`로 저장하므로
저장소 권한이 전혀 필요 없습니다. 나눠 저장할 때만 폴더 권한(`OpenDocumentTree`)을 받습니다.
`text/plain` VIEW·SEND 인텐트를 등록해서 파일 관리자에서 txt를 보내면 바로 앱으로 넘어옵니다.

### 인코딩 감지
BOM을 먼저 확인하고, 없으면 앞 256KB를 엄격 UTF-8로 디코드해봅니다. 실패하면 CP949로 판정합니다.

디코드할 때 `endOfInput=false`로 넘기는 게 중요합니다. 표본은 파일 중간에서 끊기므로
마지막 글자가 잘려 있는 게 정상인데, 이걸 오류로 보면 멀쩡한 UTF-8 한글 파일이
CP949로 읽혀 전부 깨집니다. (실제로 그랬고, 단위 테스트로 잡아 고쳤습니다.)

### 챕터 판정
17개 후보 패턴을 모두 시험해 네 지표로 점수를 매기고 1등을 고릅니다.

| 지표 | 가중치 | 의미 |
|---|---|---|
| 번호 연속성 | 42% | 숫자가 1씩 증가하는가 (결번은 부분 점수) |
| 길이 균일도 | 20% | 챕터별 길이의 변동계수 |
| 본문 커버리지 | 18% | 파일 전체에 고르게 퍼져 있는가 |
| 크기·개수 적정성 | 20% | 평균 200자 미만이면 잘못 잘린 것으로 감점 |

`< 제목 >` 형식도 잡습니다. 번호 없이 제목만 넣는 웹소설 txt가 흔한데,
이 형식이 패턴에 없으면 아무것도 못 잡고 본문의 `1.5m짜리`, `5.56mm` 같은 줄이
'숫자 + 점'에 걸려 파일이 서너 토막 납니다(실제로 그랬습니다). 그래서
`숫자 + 점`은 점 뒤에 숫자가 또 오면 소수점으로 보고 넘깁니다.

챕터 하나가 12만 자를 넘는 후보는 아예 뺍니다. 점수만으로는 0.47이 나와서
기준점(0.22)을 넘어 버리기 때문입니다. 웹소설 한 화는 길어야 3만 자입니다.

오탐 제거가 2단계로 들어갑니다. 최장 증가 부분수열로 번호 흐름에서 벗어난 검출을
걸러내고, 수열 양 끝의 급점프(중앙값 간격의 12배 초과)를 추가로 잘라냅니다.
끝에 붙은 오탐은 여전히 "증가"라서 1차만으로는 걸러지지 않기 때문입니다.

`N화` 패턴은 접두사를 선택적으로 두어 `123화`와 `제목 123화`를 한 패턴으로 잡습니다.
실제 웹소설 txt가 두 형식을 섞어 쓰는 경우가 많습니다.

### 판정 범위를 넓히지 않는 이유
안드로이드의 ICU는 `\s` 가 `\p{Z}` 를, `\d` 가 `\p{Nd}` 를 포함합니다. JVM보다 넓습니다.
기기와 맞춘다고 전각 공백·NBSP·전각 숫자까지 받도록 넓혀 봤다가 되돌렸습니다.
실제 파일에서 문제가 된 적이 없었고, 넓히면 본문 줄이 제목으로 잘못 걸립니다.

지금 코드는 원래 정규식과 같은 ASCII 범위만 봅니다. 시험이 검증하는 범위와 같습니다.
`RealFileRegressionTest` 가 실제 책 한 권 분량(375화, 세 자리 번호에 붙임표·줄표 혼용)으로
이걸 지킵니다.

### 안드로이드 정규식 (ICU)
안드로이드는 ICU 정규식 엔진을 쓰고 데스크톱 JVM(`java.util.regex`)보다 엄격합니다.
짝 없는 `}` 나 `]` 를 JVM은 그냥 글자로 받아주지만 ICU는 문법 오류로 막습니다.

`Regex("""\{(\w+)}""")` 하나 때문에 기기에서 `FileNamer` 초기화가 터져
앱이 죽었습니다. 단위 테스트 64개가 전부 통과한 상태였습니다 — 시험은 JVM에서
돌기 때문에 이 차이가 드러나지 않습니다.

그래서 `IcuRegexCompatTest`가 소스의 정규식 문자열을 직접 읽어 ICU가 거부하는
모양을 찾습니다. 지금 32개를 검사합니다. 기기 없이 잡을 수 있는 유일한 방법입니다.

### 메모리
줄마다 String 객체를 만들면 5.4MB 파일이 힙을 42MB 먹습니다. 글자 자체는 11MB인데
나머지가 객체 머리말과 참조입니다. 32만 줄이면 그 부담이 본문보다 커지고, 기기 힙이
좁으면 분석 중에 앱이 죽습니다(실제로 그랬습니다).

그래서 본문은 문자 배열 한 벌로 들고 줄은 시작·끝 위치로만 기억합니다(`TextLines`).
판정도 String을 만들지 않고 그 배열을 직접 읽습니다. 같은 파일이 33MB로 떨어지고,
48MB 힙에서도 읽기 → 판정 → 챕터 구성이 끝까지 돌아갑니다(`MemoryTest`).

그래도 죽는 경우에 대비해 마지막 오류를 파일로 남기고 다음 실행 때 보여줍니다.
복사 버튼으로 그대로 전달하면 원인을 바로 볼 수 있습니다.

### 판정 속도
32만 줄(5.4MB) 파일에서 화면이 멈춘 것처럼 보이는 문제가 있었습니다. 원인은 두 가지였습니다.

1. `^\s*(?:\S.{0,48}?\s+)?제?\s*(\d+)\s*화…` 의 게으른 수량자가 줄마다 수백 번씩
   역추적했습니다. 한글 단위 패턴 8개를 정규식 대신 직접 훑는 코드로 바꿨습니다.
2. 패턴 17개가 각자 32만 줄을 다시 훑고 줄마다 `trim()`을 다시 했습니다.
   짧고 비어 있지 않은 줄만 한 번 추려서 모든 패턴이 나눠 쓰게 했습니다.
   정규식 패턴은 줄 첫 글자로 먼저 거릅니다.

같은 규모에서 1,594ms → 196ms (데스크톱 기준, 8배). 판정 결과는 그대로입니다 —
`KoMatcherEquivalenceTest`가 무작위 6만 건을 예전 정규식과 대조해 같은 답인지 확인합니다.

분석 중에는 진행률이 화면 맨 위에 나옵니다. 예전에는 이 표시가 '생성' 카드 안에만
있어서 챕터가 나오기 전에는 아무것도 안 보였고, 그래서 멈춘 것처럼 보였습니다.

### EPUB 생성
챕터를 하나씩 출력 스트림에 바로 씁니다. 전체를 메모리에 올리지 않아 700화 이상도 문제없습니다.
`mimetype`은 규격대로 무압축·첫 항목이고, EPUB3 `nav.xhtml`과 EPUB2 호환 `toc.ncx`를
모두 넣어 구형 뷰어도 목차를 읽습니다. 표지가 있으면 `cover-image` 속성과
`<meta name="cover">`를 함께 등록합니다.

### 파일 이름
토큰: `{title} {author} {chapters} {source} {lang} {publisher} {date} {datetime} {first} {last} {vol} {vols}`

길이 제한은 글자 수가 아니라 UTF-8 **바이트** 기준(180바이트)입니다.
한글은 글자당 3바이트라 글자 수로 자르면 파일시스템 상한(255바이트)을 넘습니다.
나눠 저장할 때는 권 번호가 잘려 나가지 않게 자리를 따로 비워둡니다. 안 그러면
권마다 같은 이름이 되어 덮어쓰기가 납니다.

### 표지 찾기
표지는 '4. 표지' 카드에서 찾습니다. 검색어를 직접 고칠 수 있습니다 —
파일명에서 딴 제목에 `1-741 완` 같은 군더더기가 붙어 있으면 결과가 엉망이 됩니다.

| 출처 | 키 | 비고 |
|---|---|---|
| 네이버 이미지 | 필요 | 브라우저 '이미지' 탭과 같은 결과. 표지 찾기에 가장 잘 맞음 |
| 네이버 책 | 필요 | 출판된 책 표지 |
| 나무위키 | 없음 | 문서 앞쪽 그림을 순서대로 (웹소설은 여기 표지가 있는 경우가 많음) |
| 구글 북스 / 오픈 라이브러리 | 없음 | **제목이 실제로 맞을 때만** |

책 DB(구글북스·오픈라이브러리)는 못 찾으면 비슷해 보이는 딴 책을 돌려줍니다.
웹소설은 이 DB에 아예 없어서 그 일이 늘 일어나고, 그대로 두면 검색한 적도 없는
그림이 목록에 깔립니다. 그래서 제목이 실제로 맞는 것만 남깁니다(`relevant`).

**이미지 검색에는 공개 무료 API가 없습니다.** 구글·네이버 모두 키를 요구합니다.
키 없이 쓸 수 있는 길은 두 가지입니다.

1. 나무위키 문서 그림 (자동)
2. **[웹 이미지 검색]** 버튼 → 브라우저에서 그림을 길게 눌러 '이미지 주소 복사'
   → 앱의 '이미지 주소 붙여넣기' 칸에 붙여넣기. 저장했다면 [기기에서 고르기]도 됩니다.

넣을 때 긴 변 1600px JPEG로 맞춥니다. webp는 EPUB 규격 밖이라 안 보이는 뷰어가 있고,
원본이 너무 크면 파일만 무거워집니다.

### 서지 정보 조회
세 곳을 같이 봅니다.

- **네이버 책** — 설정에서 본인 API 키를 넣었을 때만. 출판된 책은 이쪽이 가장 정확하고
  표지도 실제 표지입니다. 키 발급: developers.naver.com (무료, 하루 25,000회).
  키는 기기 안 앱 전용 저장소에만 남습니다.
- **나무위키** — 공개 API가 없어 문서 HTML을 받아 Jsoup으로 파싱합니다. 안드로이드 앱에서는
  CORS가 적용되지 않고 사용자 기기 IP로 요청이 나가므로, 브라우저와 데이터센터 서버에서
  모두 막히던 조회가 여기서는 동작합니다. 클래스명이 난독화되어 있어 클래스 선택자 대신
  "작가", "연재처" 같은 **라벨 텍스트를 찾아 옆 칸을 읽는** 방식으로 구현했습니다.
- **위키백과** — MediaWiki API. 요약문에서 지은이·연재처를 뽑아냅니다.

'파일에서 찾기'는 네트워크를 쓰지 않고 본문 앞 400줄과 끝 60줄에서 `작가:`, `출판사 -` 같은
표기를 읽습니다. 파일에 적혀 있기만 하면 이쪽이 가장 정확합니다.

## 알려진 제약

**나무위키 파싱은 깨질 수 있습니다.** DOM 구조가 바뀌면 값을 못 읽습니다. 그때는 값이 비어
나오고 앱이 죽지는 않지만, `MetadataLookup.findByLabel`의 라벨 목록이나 탐색 방식을 손봐야 합니다.

**요청 빈도에 주의하세요.** 캐시와 최소 간격(1.2초)을 넣어뒀지만, 반복 호출이 잦으면 IP가
차단될 수 있습니다. 책 한 권당 한 번 수준이면 문제없습니다.

**라이선스.** 나무위키 본문은 CC BY-NC-SA 2.0 KR입니다. 작가명·연재처 같은 사실 정보는
저작권 대상이 아니라 자유롭게 쓸 수 있지만, 문서 설명문을 그대로 EPUB에 싣는 건 피했습니다.
배포하실 거면 이 선을 유지하세요.

**og:image 표지.** 나무위키 대표 이미지는 문서 내용과 무관한 이미지일 수 있습니다.
적용 전에 미리보기로 확인하세요.

## 검증 상태
